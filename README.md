# VOID EXTRACTOR — AI-Assisted Development Log

> **Repository:** https://github.com/niki2007/VOID-EXTRACTOR-PC-Mobile-game  
> **Project type:** Offline extraction roguelite / tactical RPG  
> **Technology:** One self-contained HTML file with embedded CSS and JavaScript  
> **Designed and directed by:** Niko (`niki2007`)  
> **Code generated and revised with:** ChatGPT, GPT-5.6 Thinking

---

## 1. What this project is

**VOID EXTRACTOR** is an experiment in building a large, playable game almost entirely through natural-language collaboration with an AI.

The central question was:

> How far can current AI go when asked to design, program, expand, debug, balance, and preserve a game over many iterations?

The project began as a request for a complex procedural RPG that could run directly in a browser. It eventually became a large extraction roguelite with procedural dungeons, randomized equipment, damage types, armor and resistances, gems, weapon mastery, persistent progression, crafting, traders, contracts, multiple operation types, locked areas, bosses, special events, endless mode, PC controls, mobile controls, and many other connected systems.

The entire game is distributed as a single HTML file. It does not require an installation, game engine, package manager, server, or internet connection after download.

---

## 2. What “AI-generated” means here

The code, interface, game systems, revisions, and most written game content were generated by ChatGPT in response to prompts.

The human contribution was still essential. Niko acted as the:

- Creative director
- Game designer
- Feature planner
- Tester
- Bug reporter
- Balance reviewer
- Product owner
- Repository publisher

The AI acted as the:

- Programmer
- Systems designer
- UI implementer
- Content generator
- Debugging assistant
- Compatibility maintainer
- Test author

This was not a one-prompt game. The project developed through a repeated loop:

1. Niko proposed a direction or feature.
2. ChatGPT designed how it should connect to existing systems.
3. ChatGPT generated or modified the HTML game.
4. The build was tested.
5. Niko played it on a real device.
6. Niko reported bugs, balance problems, or usability issues.
7. ChatGPT patched the existing build while preserving progress.
8. The process repeated.

That feedback loop is one of the most important parts of the experiment.

## 3. Original project goals

The first major RPG prompt established the basic direction:

> “Fully working RPG with procedural dungeons and millions of features sounds cool. Some random stats to items, many damage types and armor, inventory systems and procedural dungeon, maybe ‘extraction shooter like’, and rarities. Make something that is very complex but think about every feature so everything works and fits together.”

Several permanent design constraints came from this request and earlier projects:

- The game should be playable on mobile.
- It should also work on PC.
- It should be downloadable as one HTML file.
- It should work offline.
- It should not use external scripts, images, fonts, or libraries.
- Progress should save locally.
- New systems should fit the main gameplay loop.
- Updates should preserve existing progress whenever possible.
- Features should be functional rather than decorative menu entries.

These constraints shaped almost every later decision.

---

## 4. The core gameplay loop

The main loop became:

1. Prepare equipment in the hideout.
2. Choose an expedition or special operation.
3. Enter a procedurally generated raid.
4. Explore rooms, corridors, hazards, vaults, and side areas.
5. Fight enemies using turn-based movement and combat.
6. Collect randomized equipment, gems, keys, materials, ammunition, and consumables.
7. Decide whether to continue deeper or return to extraction.
8. Channel the extraction while surviving enemy pressure.
9. Keep successfully extracted loot.
10. Lose unsecured raid equipment after death.
11. Improve the operator, stash, mastery, skills, crafting options, and future loadouts.

Every large feature was intended to support this risk-versus-reward loop.

# 5. Development timeline

## Phase 1 — The first extraction RPG

The first build established the foundation:

- Procedural room-and-corridor dungeons
- Turn-based movement
- Melee and ranged combat
- Multiple damage types
- Armor and elemental resistance
- Random equipment
- Item rarities and affixes
- Inventory, stash, loadout, and secure pouch
- Equipment durability
- Ammunition and reloading
- Traders
- Crafting
- Skills
- Contracts
- Bosses
- Extraction and death-loss rules
- Local save data
- Mobile touch controls

The initial version proved that the single-file approach could support a real persistent game instead of only a short minigame.

### Early user feedback

The first important usability bugs were found by playing the game on mobile:

- The extraction results screen was vertically clipped.
- Closing an item-details window from the raid inventory closed the entire inventory instead of returning to it.

These were fixed by making the extraction report scroll correctly and adding context-aware modal navigation.

This established a recurring pattern: the AI could generate a large feature set, but real play exposed interaction problems that automated checks did not always reveal.

---

## Phase 2 — Crimson Depths

The next request greatly expanded the game:

> “Add more dungeon levels to 10, add more rarities, more items, more descriptions, more effects and equipment, make levels have different dungeon generation, add more quests and make them random and daily, add button to reroll trader with money, add more crafting possibilities, deploy to different types of dungeons, make the game red to black mode instead of blue to black.”

This phase added:

- Ten floors per standard expedition
- Different generation styles by floor range
- New equipment slots
- More rarities
- More weapons, armor, consumables, enemies, and bosses
- More status effects
- Multiple selectable dungeon zones
- Random daily contracts
- Paid trader rerolls
- Expanded crafting
- Salvaging
- A red-and-black visual redesign
- Better item descriptions and category labels

Dungeon generation was divided into stages:

- Floors 1–3: connected room sectors
- Floors 4–6: cavern-like layouts
- Floors 7–9: security mazes
- Floor 10: a final Warden arena

The original local-storage save key was deliberately retained so old progress could be migrated instead of discarded.

---

## Phase 3 — Gemforge and mastery

A later prompt requested several deeper progression systems:

> “I would do a gem system where you can put gems on weapons and armor… at least 20 different gems. Weapon mastery. Add procedural missions and dynamic events. Add prestige. Add more perks and more skills. The lower the rarity, the higher the chance to also have negative effects.”

This became the Gemforge expansion.

### Gem system

The game gained more than twenty gems, later expanding to over thirty.

The system required more than simply adding bonus items. It needed:

- Random sockets on compatible equipment
- Weapon and armor gem compatibility
- Gem qualities
- Gem stacks
- Socket insertion
- Gem removal
- Socket etching
- Save migration
- Equipment-detail integration
- Extraction and death behavior
- Salvage behavior
- Positive and negative modifiers
- Correct resistance and combat-stat recalculation

Installed gems became part of the equipment item itself, meaning they remained attached through saving, extraction, trading, equipment changes, and death.

### Weapon mastery

Weapon use began raising persistent mastery categories. Hits and kills contributed mastery experience, while mastery levels granted permanent bonuses and milestones.

Unlike temporary raid perks, mastery survived extraction, death, and prestige.

### Procedural missions and events

Individual floors began generating optional objectives and scheduled events, such as:

- Marked target elimination
- Data recovery
- Reactor sabotage
- Signal scanning
- Cache audits
- Survival objectives
- Helpful supply events
- Hostile reinforcements
- Environmental changes

### Prestige

The Echo Prestige system allowed the player to reset selected progression while preserving major collections and equipment.

Prestige rewarded permanent bonuses and Legacy upgrades, giving high-level players a reason to continue after reaching ordinary progression limits.

### Item flaws

Lower-rarity equipment became more likely to generate negative modifiers.

The interface used:

- Green text for beneficial modifiers
- Red text for harmful modifiers

This made low-rarity equipment more unpredictable rather than simply weaker.

---

## Phase 4 — Special Operations

The next major design request focused on game modes rather than stat-based difficulty:

> “The things that are in the game right now are just difficulties on the normal mode. Add special dungeon variants that can be chosen, like Fire dungeon or Ice dungeon, that have specific generation and enemies and dangers.”

Additional requested systems included:

- Tarkov/Arena Breakout-style keys and locked areas
- Locked containers
- Vertical or disconnected rooms
- Black Market
- Procurement auctions
- Named bounties
- Endless mode
- Expanded raid recap

This produced **Special Operations**.

### Special operation philosophy

Special operations were designed to change rules, movement, terrain, objectives, and extraction conditions—not only enemy health.

Examples included:

- A fire operation with heat pressure and lava-like hazards
- An ice operation with blizzards and sliding movement
- A toxic operation with spreading growth
- A storm operation with powered electrical systems
- A Blacksite heist focused on access keys, alarms, and secured objectives
- Endless Breach on a persistent map with increasingly aggressive hunting waves

### Keys and locks

The access system introduced:

- Multiple key qualities
- Key durability
- A protected keyring
- Locked doors
- Locked containers
- Optional vaults
- Forced entry
- Noise
- Damage
- Alarms
- Reinforcement consequences

Locked areas were generally optional so an unlucky key drop could not make an ordinary expedition impossible to finish.

### Vertical annexes

Ladders and disconnected annexes created spaces outside the main floor layout, including:

- Armories
- Observatories
- Command rooms
- Upper platforms
- Secure side areas

### Black Market and auctions

The Black Market introduced restricted or unusual inventory.

Daily procurement auctions asked the player to submit requested items for better rewards, creating a reason to keep items that might otherwise be sold immediately.

### Bounties

Named targets added specialized objectives and rewards, helping enemies feel more distinct than ordinary procedural spawns.

### Endless Breach

Endless mode used one persistent combat map rather than ten traditional floors.

Enemies spawned in waves and immediately hunted the player. Every several waves, the player could choose to extract or continue for greater risk and rewards.

### Raid recap

The extraction report expanded to show more than a loot list:

- Route map
- Accuracy
- Damage dealt
- Damage-type breakdown
- Exploration
- Locks used
- Annex visits
- Loot value
- Important events
- Timeline information

## Phase 5 — Gem deployment debugging

One of the most serious bugs appeared after the gem system had become complex.

The reported symptom was:

> “When I put a gem on anything and try to play, it doesn’t work, and when I click deploy it just puts me back to menu.”

The failure was traced to elemental armor gems. Their modifiers attempted to write resistance values before the raid resistance object had been initialized. Deployment stopped halfway through player creation.

A second problem meant some gem resistances could later be overwritten during stat recalculation.

The fix included:

- Correct stat-initialization order
- Defensive socket-data validation
- Preservation of gem resistance bonuses
- Cleanup of malformed legacy socket entries
- Restoration of raid pack and counters if deployment fails
- Testing every gem type across every operation

This was a useful example of a system working in isolation but failing when connected to the complete deployment pipeline.

---

## Phase 6 — Gem navigation and loot balancing

Another user-reported issue occurred after consuming the final gem in a stack:

> “When I click Socket on gem, then put the gem on a weapon, then try to close the gem menu, it says ‘Gem stack no longer exists.’”

The gem had actually been inserted correctly. The problem was that the close action attempted to reopen a gem stack that had just reached zero and had been removed.

The fix changed the return target:

- If the stack still exists, return to the socket-selection list.
- If the final gem was consumed, return to the equipment or stash screen.

This update also improved:

- Gem and key descriptions
- Installed-gem modifier visibility
- Negative gem modifiers
- Operation selection
- Extraction channel length
- Loot-rarity balance

### Rarity rebalance

Easy expeditions were producing Epic and Relic items too frequently.

The first idea—simply capping forbidden rarities—could have made the maximum allowed rarity appear too often. Instead, over-tier rolls were downshifted through lower rarity bands.

The result was intended to make early expeditions mostly produce Common and Uncommon equipment, while still allowing occasional exciting drops without making high rarity routine.

---

## Phase 7 — PC and mobile usability

A later expansion focused on clarity and dual-platform support:

> “Add small text next to the controls that tells me how to control it on PC… fix the map after extraction… add two more Standard Expeditions… add DEV mode… add descriptions in Workshop… extend the Field Manual.”

This phase added:

- PC keyboard bindings
- Key labels displayed on action buttons
- Two additional standard expeditions
- DEV mode
- Workshop recipe explanations
- A larger Field Manual
- Correct extraction-map proportions

### PC controls

Movement supported WASD and arrow keys, while combat and interface actions gained dedicated keyboard shortcuts.

The key hints were placed directly on the relevant controls so players did not need to search a manual during combat.

### Additional expeditions

Two more standard expeditions were added with unique mechanics rather than only different names:

- **Graviton Quarry** — gravity anchors and displacement effects
- **Sanguine Archive** — memory nodes and recurring echo enemies

### DEV mode

DEV mode was deliberately limited. It did not add invincibility or automatic combat wins.

It removed currency and skill-point requirements for testing:

- Free purchases
- Free rerolls
- Free repairs
- Free credit-based socket services
- Skill upgrades without spending points

This made it easier to test late-game equipment and systems.

# 7. Technical approach

## Single-file architecture

The entire application is stored in one HTML file containing:

- HTML interface structure
- CSS styling and responsive layouts
- JavaScript game logic
- Canvas rendering
- Procedural generation
- Game content definitions
- Save migration
- Audio generation
- Touch and keyboard controls

No build process is required.

## Offline operation

The project was intentionally designed without:

- External JavaScript libraries
- Remote images
- External fonts
- CSS imports
- Network APIs
- Accounts
- Online servers

Browser features such as Canvas, Web Audio, vibration, file export/import, and `localStorage` are used where available.

## Persistent saves

The save key remained:

```text
void_extractor_rpg_v1
```

Keeping the same key allowed later versions to migrate older profiles.

New systems added defaults during loading rather than replacing the entire profile. This helped preserve:

- Credits
- Level and experience
- Stash items
- Equipment
- Gems
- Mastery
- Skills
- Contracts
- Records
- Settings

Save export and import were also added because mobile browsers may treat the same HTML file in different folders as separate storage origins.

## Procedural systems

Random generation is used for:

- Dungeon layouts
- Enemy placements
- Enemy mutations
- Equipment bases
- Item levels
- Rarities
- Affixes
- Flaws
- Sockets
- Gems
- Daily trader inventory
- Contracts
- Bounties
- Auctions
- Raid missions
- Dynamic events
- Loot containers

Procedural generation creates a large number of combinations without requiring separate handcrafted files for every result.

# 9. Design principles that emerged

## Add systems on top instead of deleting old content

A repeated goal was to preserve earlier work.

New updates generally:

- Kept old items valid
- Kept the save key
- Added migration defaults
- Added new operations beside existing expeditions
- Extended detail panels
- Expanded records
- Preserved existing currencies and progression

## Features should connect to the extraction loop

The project avoided adding features only because they sounded impressive.

Examples:

- Gems affect equipment risk because they are attached to gear.
- Keys survive through the protected keyring and create optional risk.
- Auctions make extracted items economically useful.
- Weapon mastery rewards repeated weapon use.
- Prestige preserves long-term goals.
- Annexes create optional exploration.
- Rarity curves make operation selection meaningful.
- Longer extraction channels increase danger in harder operations.

## Mobile usability matters

The game began as a mobile-focused project, so several details were important:

- Large unselectable buttons
- Safe-area padding
- Touch-friendly controls
- Responsive windows
- Scrollable reports
- Player-centered dungeon camera
- Haptic feedback where supported
- Reduced-motion option
- No hover-only interactions

Later, PC controls were layered on top without removing the mobile interface.

# 10. Known limitations

This project is an AI-development experiment, not a traditional commercial production pipeline.

Important limitations include:

- A single HTML file eventually becomes difficult to maintain.
- Large functions and appended version patches can make the code harder to read.
- Browser storage behavior differs between devices and file locations.
- Automated testing cannot fully replace long-term human playtesting.
- Procedural systems can still produce unusual balance combinations.
- Browser features such as vibration, audio, fullscreen, and file access vary.
- AI-generated code can introduce regressions when systems interact.
- Performance depends on the browser and device.
- The project does not currently use a formal engine, module system, source map, or unit-test framework.

For a long-term production version, the game would ideally be divided into modules such as:

- Core state
- Save system
- Item generation
- Combat
- Dungeon generation
- UI
- Audio
- Operations
- Tests
- Content data

The single-file format was retained because it was one of the experiment’s main constraints.

# 11. What this experiment demonstrates

VOID EXTRACTOR demonstrates that current AI can:

- Produce a functional game from natural-language requirements
- Maintain a large evolving codebase within one file
- Add interconnected progression systems
- Interpret informal design feedback
- Debug reported runtime failures
- Preserve save compatibility
- Generate large amounts of game content
- Build mobile and desktop controls
- Perform automated smoke and state-transition tests
- Iterate over many versions without a conventional game engine

It also demonstrates what AI does **not** remove from game development:

- The need for a clear creative direction
- The importance of testing
- The value of player feedback
- The need for balance decisions
- The need to prioritize features
- The need to identify bad interaction design
- The need to verify that systems actually work together

The AI wrote the code, but the game became what it is because a human repeatedly played it, challenged it, found problems, and decided what should come next.
